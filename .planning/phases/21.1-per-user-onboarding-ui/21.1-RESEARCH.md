## Summary

Phase 21.1 is a purely iOS/SwiftUI task. The backend is fully implemented and verified (Phase 21). The work is: build 7 new Swift files, extend 3 existing files, and wire the whole onboarding TabView carousel into the app root.

All design decisions are locked in CONTEXT.md and the UI-SPEC has been written to near-implementation level. Research confirms that the patterns specified (TabView `.page` style, ASWebAuthenticationSession for OAuth, `@EnvironmentObject` + `@StateObject` state propagation, Keychain for persistence) are the correct idiomatic SwiftUI approaches. No alternative library research is needed — the stack is pinned.

The key complexity areas are: (1) gate logic for forward-only swipe prevention using `onChange`, (2) threading the `IntegrationState` object from `dAIlyApp` level down to child views and back up via deep-link callbacks, and (3) the `ASWebAuthenticationSession` presentation context provider pattern on iOS.

**Primary recommendation:** Implement in 4 waves: state/model layer → view files → AuthService extensions → app wiring (root routing + onOpenURL). Test each wave before advancing.

### Pattern 1: Forward-Only TabView Gate

**What:** Clamp `currentTab` via `.onChange(of:)` whenever the user swipes forward past an allowed maximum tab.

**When to use:** Standard approach for wizard flows in SwiftUI where back-swipe should work but forward-skip should not.

```swift
// Source: UI-SPEC §Root: OnboardingView
.onChange(of: currentTab) { newValue in
    if newValue > allowedMaxTab {
        currentTab = allowedMaxTab
    }
}

private var allowedMaxTab: Int {
    if !appState.hasAccessToken { return 1 }
    if !integrationState.atLeastOneConnected { return 4 }
    if !scheduleSaved { return 5 }
    return 6
}
```

**Critical:** `allowedMaxTab` must be a computed property on `OnboardingView` that reacts to `@EnvironmentObject appState` and `@StateObject integrationState`. Since `integrationState` is `@Published`, any change to `connectedProviders` automatically re-evaluates the clamp.

### Pattern 2: IntegrationState Lifted to dAIlyApp

**What:** `IntegrationState` is declared as `@StateObject` in `dAIlyApp`, injected via `.environmentObject()`, and read in both `OnboardingView` and `dAIlyApp.onOpenURL`.

**Why:** The `onOpenURL` handler lives in `dAIlyApp`. It must call `integrationState.markConnected(provider:)` when `/oauth/success` arrives. If `IntegrationState` only lived in `OnboardingView`, `dAIlyApp.onOpenURL` cannot reach it.

```swift
// dAIlyApp.swift
@StateObject private var integrationState = IntegrationState()

var body: some Scene {
    WindowGroup {
        Group { ... }
        .environmentObject(appState)
        .environmentObject(integrationState)
    }
}
```

**Note from UI-SPEC:** This is confirmed as the preferred approach over keeping state inside `OnboardingView`. [VERIFIED: 21.1-UI-SPEC.md §Deep-Link Wiring]

### Pattern 3: ASWebAuthenticationSession with Universal Links

**What:** Open OAuth URL in `ASWebAuthenticationSession` with `callbackURLScheme: nil` (Universal Links, not custom schemes). The session completes when the system receives the Universal Link redirect.

**Key detail:** The session's completion handler only fires for custom URL scheme callbacks. For Universal Link callbacks, the session is dismissed automatically and `dAIlyApp.onOpenURL` fires. This means the continuation in `openOAuthSession` will NOT be resumed by the ASWebAuthenticationSession callback — it must be resumed differently.

**Correct pattern:** Rather than `withCheckedThrowingContinuation`, use a simpler fire-and-forget approach: start the session, set `isConnecting = false` when session starts or fails, and let `onOpenURL` update `integrationState` reactively. The UI updates via `@Published` without needing the continuation to resolve.

```swift
// AuthService.swift
@MainActor
public func openOAuthSession(url: URL) throws {
    let session = ASWebAuthenticationSession(
        url: url,
        callbackURLScheme: nil   // Universal Links: system handles redirect
    ) { _, error in
        // Only fires on custom scheme callbacks — not needed for Universal Links
    }
    session.presentationContextProvider = windowSceneProvider
    session.prefersEphemeralWebBrowserSession = false
    guard session.start() else {
        throw AuthError.network("ASWebAuthenticationSession failed to start")
    }
}
```

**Presentation context:** `ASWebAuthenticationSession` requires a `presentationContextProvider` conforming to `ASWebAuthenticationPresentationContextProviding`. The simplest approach: make `AuthService` conform, returning the active window via `UIApplication.shared.connectedScenes`.

**Warning — known pitfall:** If `callbackURLScheme` is non-nil AND a Universal Link is used, the session may not dismiss correctly on some iOS versions. Always use `nil` for Universal Link redirects. [ASSUMED — based on Apple documentation patterns, behavior verified conceptually]

### Pattern 4: Auto-Advance After Auth

**What:** `OnboardingView` observes `appState.hasAccessToken` and auto-advances from tab 1 → tab 2 when it becomes true (after PairingView verifies the magic link code).

```swift
// OnboardingView.swift
.onChange(of: appState.hasAccessToken) { newValue in
    if newValue && currentTab == 1 {
        withAnimation { currentTab = 2 }
    }
}
```

**Why:** PairingView doesn't have an explicit "Continue" button — it sets `appState.hasAccessToken = true` and transitions internally. The parent OnboardingView must watch this published property.

### Pattern 5: API Path Correction

**Critical finding:** The UI-SPEC references `PUT /users/preferences` but the actual backend endpoint is `PUT /users/me/preferences`. [VERIFIED: `src/daily/users/router.py` line 97]

All `AuthService` calls must use `/users/me/preferences`, not `/users/preferences`.

Similarly, `GET /users/me/integrations` returns `{google: bool, microsoft: bool, slack: bool}` but this endpoint is not used during onboarding (the connection state is tracked in `IntegrationState` in-memory).

### Anti-Patterns to Avoid

- **Lifting `IntegrationState` into `AppState`:** AppState is for persistence-backed auth state. IntegrationState is ephemeral onboarding session state. Keep them separate — both as `@StateObject` in `dAIlyApp`.
- **Using `withCheckedThrowingContinuation` for Universal Link OAuth:** The continuation will never be resumed by the ASWebAuthenticationSession callback for Universal Link redirects. Use fire-and-forget instead.
- **Calling `PUT /users/preferences` (wrong path):** Backend path is `/users/me/preferences`. Using the wrong path returns 404.
- **Writing `onboarding_complete` before `savePreferences` succeeds:** Always write the Keychain flag inside the `do` block after a successful API call, not before.
- **Presenting OnboardingView after VoiceView is active:** Once `hasCompletedOnboarding = true`, do not show OnboardingView even transiently. The root routing switch must be instant.

## Common Pitfalls

### Pitfall 1: API path mismatch (`/users/preferences` vs `/users/me/preferences`)
**What goes wrong:** 404 on preferences save, `ScheduleView` shows persistent error.
**Why it happens:** UI-SPEC uses a slightly wrong path. Actual backend uses `/users/me/preferences`.
**How to avoid:** Use `/users/me/preferences` in `AuthService.savePreferences`.
**Warning signs:** HTTP 404 in logs when saving schedule.

### Pitfall 2: IntegrationState not accessible in onOpenURL
**What goes wrong:** `/oauth/success` deep link arrives, but `integrationState.markConnected` cannot be called — `IntegrationView` stays in "connecting" state indefinitely.
**Why it happens:** If `IntegrationState` is only `@StateObject` inside `OnboardingView`, `dAIlyApp.onOpenURL` can't reference it.
**How to avoid:** Declare `IntegrationState` as `@StateObject` in `dAIlyApp`, inject via `.environmentObject()`.

### Pitfall 3: Gate logic race condition on auth
**What goes wrong:** User completes pairing, `hasAccessToken` flips, but `allowedMaxTab` still returns 1 because the observer hasn't re-evaluated yet.
**Why it happens:** SwiftUI's reactive graph evaluates synchronously, but `onChange` fires after the render pass.
**How to avoid:** Use `withAnimation { currentTab = 2 }` inside the `onChange` — the animation delay is enough for `allowedMaxTab` to recalculate before the tab change clamp runs.

### Pitfall 4: OAuth session dismissed before deep link fires
**What goes wrong:** `ASWebAuthenticationSession` completes (browser closes) but `/oauth/success` Universal Link arrives slightly later. If `isConnecting` is set to `false` too early, the user sees a confusing intermediate state.
**Why it happens:** Universal Link delivery is asynchronous via the system's URL handler.
**How to avoid:** Only set `isConnecting = false` after `integrationState.markConnected` is called (i.e., in response to the deep link), not when the session's completion handler fires.

### Pitfall 5: `onboarding_complete` Keychain key survives uninstall on older iOS
**What goes wrong:** User reinstalls app, Keychain key `onboarding_complete` still exists (Keychain persists across installs by default), app skips onboarding for a fresh user.
**Why it happens:** iOS Keychain items are not deleted on app uninstall unless `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` is used or a first-launch cleanup explicitly runs.
**How to avoid:** The project already has `FirstLaunchCleanup.runIfNeeded()` in `dAIlyApp.init()` [VERIFIED: dAIlyApp.swift line 10]. Confirm that `clearAll()` on `KeychainStore` is called there — if so, `onboarding_complete` will be cleared on first launch post-reinstall automatically.

### Pitfall 6: `@MainActor` isolation on `AuthService` + `ASWebAuthenticationSession`
**What goes wrong:** `ASWebAuthenticationSession.start()` must be called on the main thread. `AuthService` is already `@MainActor` [VERIFIED: AuthService.swift line 21], so any new OAuth method automatically satisfies this.
**How to avoid:** Keep new `openOAuthSession` method inside `AuthService` (which is `@MainActor`). Do not extract it to a background actor.

### Verified: AuthService getJSON helper (missing — must add)

The existing `AuthService` only has `postJSON`. New methods need `getJSON` and `putJSON`. Pattern mirrors `postJSON` exactly:

```swift
// AuthService.swift — private helper (mirrors postJSON)
private func getJSON<T: Decodable>(path: String, expecting: T.Type) async throws -> T {
    var req = URLRequest(url: baseURL.appendingPathComponent(path))
    req.httpMethod = "GET"
    // Add Bearer token from Keychain
    if let token = keychain.load(key: "access_token") {
        req.setValue("Bearer \(token)", forHTTPHeaderField: "Authorization")
    }
    // ... same error handling as postJSON
}
// Source: AuthService.swift postJSON pattern (existing)
```

**Note:** `postJSON` does NOT currently add a Bearer token header [VERIFIED: AuthService.swift lines 87–117]. New integration and preferences endpoints require authentication. Both `getJSON` and `putJSON` must add the `Authorization: Bearer {token}` header from Keychain.

## Open Questions

1. **What does `FirstLaunchCleanup.runIfNeeded()` actually clear?**
   - What we know: It exists in `dAIlyApp.init()` [VERIFIED]. `KeychainStore.clearAll()` deletes all items under the service.
   - What's unclear: Whether it was updated to also handle `onboarding_complete` (a new key), or whether `clearAll()` covers it by design (it removes ALL keys for the service — so yes, it would).
   - Recommendation: Read `ios/dAIly/auth/` for a `FirstLaunchCleanup.swift` file before implementing. If `clearAll()` is used, `onboarding_complete` is automatically covered.

2. **Does the `ASWebAuthenticationSession` presentation context need a specific implementation?**
   - What we know: `AuthService` is `@MainActor`, so it has access to the main thread. Getting `UIWindowScene` requires `UIApplication.shared.connectedScenes`.
   - What's unclear: Whether the app uses SceneDelegate or pure SwiftUI lifecycle — it uses `@main struct dAIlyApp: App` (pure SwiftUI lifecycle) [VERIFIED], so `UIApplication.shared.connectedScenes` is the correct approach.
   - Recommendation: Create a simple `private class WindowSceneProvider: NSObject, ASWebAuthenticationPresentationContextProviding` inside AuthService.swift.
