# Phase 21.1: Per-User Onboarding UI - Context

**Gathered:** 2026-05-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Native iOS onboarding screens: welcome/signup, OAuth connect cards (Google, Microsoft, Slack), briefing schedule picker. Users complete full onboarding in-app. This is the frontend counterpart to the Phase 21 backend — all API endpoints and backend OAuth flows are already implemented.

</domain>

<decisions>
## Implementation Decisions

### Navigation Architecture
- **D-01:** TabView with `.page` style (swipeable carousel). This is the native iOS onboarding pattern — progress dots via `tabViewStyle(.page)` + `indexViewStyle(.page(backgroundDisplayMode: .always))`.
- **D-02:** Forward-only gating — swipe-to-advance is disabled on the TabView. The user advances via button only, and only when the step's condition is met (e.g. at least one integration connected before advancing past integrations).
- **D-03:** Back navigation (swipe left) works naturally — user can review a previous step but cannot skip forward past a gate.

### Onboarding State Persistence
- **D-04:** Keychain flag `onboarding_complete` (Bool). Written to Keychain at the end of schedule setup (completion screen CTA tap).
- **D-05:** `AppState` grows a `hasCompletedOnboarding: Bool` property alongside `hasAccessToken`. App routing: `hasAccessToken && hasCompletedOnboarding` → VoiceView; `hasAccessToken && !hasCompletedOnboarding` → onboarding TabView; `!hasAccessToken` → PairingView (which is now page 1 of the onboarding flow).
- **D-06:** Network-based onboarding state sync (via `/users/me`) is deferred — the Keychain flag is sufficient for Phase 21.1.

### Welcome Screen
- **D-07:** A branded welcome screen is the first page of the TabView carousel, before email entry. Content: app name, one-line value prop ("Your AI daily briefing, every morning"), single "Get started" CTA.
- **D-08:** Tapping "Get started" advances to the email entry page (PairingView becomes page 2 of the onboarding flow, not the app root).

### Integration Screens
- **D-09:** 3 separate TabView pages — one per provider: Google → Microsoft → Slack. Matches Phase 21 D-10 exactly.
- **D-10:** Each integration page shows: provider name, description of what data is accessed (Gmail + Google Calendar; Outlook + Teams; Slack channels and DMs), a Connect button, and a Skip option.
- **D-11:** After successful connection, the Connect button is replaced with a green checkmark and the connected account email (Phase 21 D-11).
- **D-12:** At least one integration must be connected before the user can advance past the Slack page (the last integration page). The Skip option on the Slack page is hidden until at least one provider is connected (Phase 21 D-12).
- **D-13:** OAuth via ASWebAuthenticationSession (Phase 21 D-09). App calls `GET /integrations/{provider}/connect` to get the authorization URL, opens it in ASWebAuthenticationSession, waits for the Universal Link callback (`/oauth/success?provider={provider}`).

### Briefing Schedule Screen
- **D-14:** iOS native `DatePicker` in `.hourAndMinute` mode. Default: 7:00 AM (Phase 21 D-13).
- **D-15:** Timezone auto-detected from `TimeZone.current` and sent with the schedule save request (Phase 21 D-14). No user-facing timezone picker.
- **D-16:** Save/Continue button calls `PUT /users/preferences` with `briefing_time` and `timezone`. On success, write `onboarding_complete` to Keychain and advance to the completion screen.

### Completion Screen
- **D-17:** "You're all set" screen after schedule is saved. Shows a summary of what was configured: briefing time (e.g. "Briefing at 7:00 AM") and connected providers (e.g. "Google connected").
- **D-18:** Single CTA: "Start talking to dAIly." Tapping it transitions to VoiceView (sets `appState.hasCompletedOnboarding = true`).

### Claude's Discretion
- Visual design, colors, animation — keep consistent with existing iOS app aesthetic (minimal, functional SwiftUI).
- Exact wording on integration permission descriptions.
- Error handling for failed OAuth flows (generic retry or inline error message is fine).
- Progress dot styling and color.
- Transition animation between pages.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ios/dAIly/views/PairingView.swift` — Email entry + magic link send + OTP verify. Used as-is as page 2 of the onboarding TabView.
- `ios/dAIly/auth/KeychainStore.swift` — Keychain read/write. Used to persist `onboarding_complete` flag.
- `ios/dAIly/auth/AuthService.swift` — Network call pattern (async/await, Bearer JWT). New integration connect methods follow the same shape.
- `ios/dAIly/views/ConnectionIndicator.swift` — Existing indicator component — may be reusable for integration connection state.

### Established Patterns
- SwiftUI + `@StateObject` / `@EnvironmentObject` for shared state via `AppState`.
- Async/await for all network calls (`Task { try? await ... }`).
- `KeychainStore.shared.load/save` for token and flag persistence.
- Minimal functional UI — no heavy theming library in use.

### Integration Points
- `dAIlyApp.swift` root routing: extend `if appState.hasAccessToken` branch to also check `appState.hasCompletedOnboarding`.
- `AppState`: add `hasCompletedOnboarding: Bool` initialized from `KeychainStore.shared.load(key: "onboarding_complete")`.
- New `OnboardingView` (TabView carousel) wired as the root when `hasAccessToken && !hasCompletedOnboarding`.
- OAuth Universal Link handler in `dAIlyApp.onOpenURL`: currently handles pair codes — needs to also handle `/oauth/success?provider=` deep links and relay to `OnboardingView`.

</code_context>

<specifics>
## Specific Ideas

- TabView `.page` style with progress dots communicates step position without custom progress bar code.
- The "You're all set" screen should summarise: briefing time + which providers are connected — makes the user feel their setup was acknowledged.
- `onOpenURL` already exists in `dAIlyApp.swift` for pair code handling — extend it to handle `/oauth/success` rather than adding a second handler.

</specifics>

<deferred>
## Deferred Ideas

- Network-based onboarding state sync (`/users/me` returns `onboarding_complete`) — correct for multi-device, deferred to a later phase.
- Re-onboarding flow for adding integrations post-setup — belongs in a settings/preferences phase.
- Animation polish on completion screen — left to Claude's discretion.

</deferred>
