# Phase 20.1 — End-to-End Smoke Test Runbook

**Purpose:** Confirm the full voice loop (worker → LiveKit → mobile client) works end-to-end with a real iOS or Android device.

---

## Pre-conditions

1. `.env` file at project root has valid values for:
   - `OPENAI_API_KEY`
   - `DEEPGRAM_API_KEY`
   - `CARTESIA_API_KEY`
   - `JWT_SECRET`
   - `VAULT_KEY`

2. A briefing has been pre-cached in Redis for `user_id=1`. Quickest path:
   - Run `uv run daily chat` on the host to trigger the briefing pipeline, OR
   - Seed Redis manually: `redis-cli SET briefing:1 "Good morning. Your briefing is ready." EX 86400`

3. iOS app (or Android app) `Config.backendBaseURL` is set to a tunnel URL pointing at `localhost:8000`.

---

## Steps

### 1. Start the full stack

```bash
docker compose up -d
```

Verify all services are running:

```bash
docker compose ps
```

Expected: `postgres`, `redis`, `livekit`, `worker` all show `running`.

### 2. Start FastAPI on the host

```bash
uv run uvicorn daily.main:app --reload --port 8000
```

### 3. Start a tunnel

```bash
cloudflared tunnel --url http://localhost:8000
```

Copy the tunnel URL (e.g. `https://xxxx.trycloudflare.com`) and set it as `backendBaseURL` in `ios/dAIly/Config.swift` (or Android equivalent).

### 4. Pair the device

Use the magic-link pairing flow from Phase 19. Confirm an access JWT is received and stored in Keychain.

### 5. Start a voice session

Tap the voice button in the iOS app. The app calls `POST /livekit/token`, receives a room JWT, and joins a room named `session-1-{timestamp}`.

### 6. Observe state transitions

Within ~3 seconds, the iOS app state should transition:
`.connecting` → `.listening` → `.speaking`

### 7. Listen for the briefing

You should hear the briefing narrative spoken via Cartesia voice through the device speaker.

If you hear silence, check:
```bash
docker compose logs worker --tail=100
```

Look for: `worker: speaking briefing` or `worker: no cached briefing`.

### 8. Test voice turns

After the briefing finishes, say: _"What's the first email about?"_ or _"Tell me more."_

Expected: app transitions `.speaking` → `.listening` → `.speaking` with a coherent response within ~3 seconds.

### 9. Test clean disconnect

Say _"exit"_ or close the session in the app. Confirm the agent disconnects cleanly.

Expected log line in `docker compose logs worker`: `worker: disconnecting` or room lifecycle event.

### 10. (Optional) Android coverage

Repeat steps 5–9 with the Android app.

---

## Expected Outcomes

- Briefing audio plays end-to-end on first connect.
- Voice turns work: STT transcribes correctly, LLM responds in <3s, TTS plays back.
- No `Traceback` / 5xx / disconnect errors in `docker compose logs worker` during the session.

---

## Failure Modes

| Symptom | Likely Cause | Fix |
|---------|-------------|-----|
| Briefing silent | Redis cache miss OR DailyAgentLLM not feeding tokens | Seed Redis with `redis-cli SET briefing:1 "..." EX 86400` |
| Audio one-way (hear briefing but mic doesn't reach agent) | Deepgram plugin misconfigured | Check `DEEPGRAM_API_KEY` in `.env` and worker logs |
| Agent disconnects immediately | Room name doesn't match `session-{user_id}-{ts}` pattern | Check `parse_user_id_from_room` logs in worker |
| Worker exits on startup | Missing env var | Check `docker compose logs worker` for Settings validation errors |

---

## Teardown

```bash
docker compose down
```
